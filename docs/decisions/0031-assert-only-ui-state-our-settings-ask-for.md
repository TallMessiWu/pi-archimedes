# Assert only the `ctx.ui` state an archimedes setting asks for; restore — never assert — what we merely took

`packages/ui/src/index.ts` called `ctx.ui.setWorkingIndicator(undefined)` on every `session_start`, with the comment's justification that this "hands the indicator back to pi, so the row a user sees is pi's default". It does — and it also wipes any indicator any other extension set, because the setter is an unskeyed overwrite (`this.workingIndicatorOptions = options`, `interactive-mode.js:1831-1837`) and last writer wins. That is how `pi-archimedes@2.11.1` deleted a user's custom spinner (#147). We decided to stop asserting UI state no archimedes setting asked us to change, and to limit ourselves, for state a setting *does* govern, to writing the direction that setting demands. The rule binds every package that calls a `ctx.ui` setter, not just the working row.

The deciding fact is that **we never set a working indicator**: both call sites passed `undefined`, and no setting in `archimedes.ui` configures frames or an interval. So the call asserted a claim we do not hold, bought nothing, and cost another extension its spinner. `setWorkingVisible` and `setHiddenThinkingLabel` are different in kind — `editorSpinBorder` and `labelText` are real user settings — so they stay asserted, but `session_start` now writes only `setWorkingVisible(false)`, and only while the border spinner is on; asserting `true` was our way of un-hiding pi's row for a user who never asked, and it also un-hid it for any extension that deliberately hid it to draw its own spinner.

**Considered Options**

- **Fix the indicator only, leave `setWorkingVisible(true)` asserted at `session_start`** — rejected: the reporter's own workaround shows the sibling bug. An extension supplying custom frames usually hides pi's row too, and our unconditional `true` puts it back, giving that user a doubled "Working" row instead of a missing spinner. Same session_start, same class of wipe.
- **Also guard `setHiddenThinkingLabel` — skip the write when `labelText` equals pi's default** — rejected, and deliberately left as a named known limitation. The guard can only be written by duplicating pi's *private* default (`defaultHiddenThinkingLabel = "Thinking..."`, `interactive-mode.js:272`, no accessor) as a literal in our source; when pi changes that string the guard silently inverts and we are wiping again. It is also not the same problem: `labelText` is an archimedes setting, so two extensions disagreeing over it is a product conflict rather than us asserting a claim we lack.
- **Run our handler later, or document that extension authors must re-apply on `before_agent_start`** (the issue's own suggestions) — rejected: pi does not sort extension files (zero `sort()` calls in `core/extensions/loader.js`; discovery is raw `readdirSync` order over project dir, then global dir, then configured paths), so "archimedes runs last" is an accident of filesystem order and any design that depends on being last is unsound. And `before_agent_start` fires per prompt, not per session — a workaround, not a contract.

**Consequences**

- **Reliance on pi's reset, stated rather than assumed.** Not asserting `visible = true` means the row's resting state belongs to pi. It does restore it on every path that could leave it hidden — fresh startup (`workingVisible = true`, `:269`), session replacement via `/new`, `/resume`, `/fork` (`beforeSessionInvalidate` → `resetExtensionUI()`, `agent-session-runtime.js:111`, `interactive-mode.js:1921`), and `/reload` (`:5378`) — which also restores the indicator (`setWorkingIndicator()`, `:1922`). Any extension that wants custom frames must therefore re-apply it per session, and that obligation is pi's existing contract, not one we were enforcing. We already depended on this reset for the row's visibility; the code comment at the call site said so.
- **Only `session_start` was capable of causing #147.** All extensions' `session_start` handlers run together in load order, but `session_shutdown` is always followed by pi's own `resetExtensionUI()` and then by `session_start` on the fresh runner (`agent-session-runtime.js:106-111` → `agent-session.js:2651`), so anything re-applied in the new session wins over our shutdown call regardless of load order. The `session_shutdown` handback is therefore guarded (`if (spinFlag)`) for truthfulness — we restore what we hid, we do not assert a default — not because it was a second wipe site. We patched one site, and the docs should not imply otherwise.
- `session_shutdown` keeps handing back `setHiddenThinkingLabel(undefined)` and `setEditorComponent(undefined)`: both undo state we demonstrably took, which is the restoring half of the rule.
- Known limitation, unresolved on purpose: another extension's `setHiddenThinkingLabel` still loses to our `labelText` default at `session_start`. If pi ever exposes the default or an accessor for it, that guard becomes cheap and this consequence should be revisited.
